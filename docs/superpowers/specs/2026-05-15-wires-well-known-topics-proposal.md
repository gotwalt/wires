# Well-Known Topics — Design Proposal

**Status:** Proposal (RFC) — pending review.
**Date:** 2026-05-15
**Depends on:** Substrate v1, Responder-driven pairing v1.

> This document is a proposal, not an accepted design. It exists to gather feedback before any implementation work is scheduled. Please leave comments inline (or in a thread linking back to this file) and we will converge on a final design — or reject — before opening a `docs/superpowers/plans/` plan.

---

## 1. Problem

Every topic id in wires today is a random 32 bytes generated by `wires topic create` and persisted into the agent's `topic_names.json`. For an agent to subscribe to a topic it must learn the id through one of:

- It created the topic (id is already in its own state).
- It received the id in a `PairGrant` (the operator explicitly named the topic when approving the agent).
- It was told the id out-of-band (paste, QR, chat, etc.).

This works fine for ad-hoc household topics (`home.notes`, `fridge.events`). It is friction for **service-category topics** that every household plausibly wants — email, sms, telephony, utility telemetry, etc. Onboarding an agent that "speaks email" today requires the operator to enumerate the household's email topic id when approving the pair, even though the *intent* — "be the household's email topic" — is universal across deployments.

We want: an agent that speaks a well-known service category can compute the household's topic id for that category from the root pubkey alone, with no out-of-band id coordination.

## 2. Non-goals

- **Content schemas.** Well-known categories carry freeform content; agents that consume them coordinate on meaning at the LLM/prompt layer. We are explicitly avoiding the bikeshed-bait of formal field schemas.
- **A registry server or runtime catalog distribution.** The catalog is a flat constant in `wires-core`, extended by PR to this repo.
- **Multi-instance scoping in v1.** "Work email" vs "personal email" remains an ad-hoc random-id topic; the well-known catalog is one entry per category per household.
- **Backfilling existing random-id topics.** Households that already have a `comms.email` random-id topic are not auto-migrated; see §6 open questions.

## 3. Proposed design

### 3.1 Derivation

Add a per-household derivation for topic ids in a fixed catalog of category names:

```
topic_id = BLAKE3("wires.well-known.v1\0" || category || "\0" || root_pubkey_bytes)
```

Null separators between the namespace, the category, and the root bytes prevent prefix-collision ambiguities (e.g. `category="foo"` + root `[0xba, 0xad, …]` must not collide with `category="fooba"` + root `[0xad, …]`).

This mirrors the existing `derived_topic_id(domain, root_pubkey_hex)` pattern already used for `wires.firehose.v1` and `wires.caps.v1` in `crates/wires-node/src/config.rs:39-46`. We are not inventing a new derivation scheme — we are extending an established one with an explicit category-namespaced subdomain.

### 3.2 Catalog

A flat array of canonical category names lives in `wires-core::well_known::CATALOG`. Strawman initial set:

- `comms.email`
- `comms.sms`
- `comms.telephony`
- `utility.power`

Adding to the catalog is a PR to this repo. The catalog is the wire-protocol authority; every wires binary that links `wires-core` agrees on which names derive.

### 3.3 CLI behaviour

`wires topic create <name>`:

- If `name` is in the catalog → derive the id; print `Using well-known derivation for '<name>' (category)`.
- Otherwise → generate a random id, as today.

No new flag. The catalog is the sole gate. Everything downstream of id selection — epoch key generation, self-cap minting when a root key is present, `topic_names.json` persistence — is identical to today.

### 3.4 What stays unchanged

- **Epoch keys** are still random per-topic and distributed only via `PairGrant`. Well-known derivation only deterministicizes the *id*, not the *key*. A well-known topic id is publicly computable from `(catalog, root_pubkey)`; the epoch key is still a per-household secret.
- **Capabilities** are still operator-minted via `pair-approve` and scoped to topic names via the existing glob system. Well-known names participate in cap globs exactly like ad-hoc names.
- **Wire format, gossip, replay, host control protocol.** None change.
- **Host code.** No changes to `wires-host`. The host has never cared how an agent picked its topic id, only that it was registered.

## 4. Threat model & metadata implications

### 4.1 Properties preserved

- **AEAD confidentiality of content.** Unchanged. Ciphertext is opaque to anyone without the epoch key.
- **Cap-gated publishing.** Unchanged. Receivers still verify cap + signature at decrypt time.
- **Per-publisher hash chains.** Unchanged.
- **Host blindness to ciphertext.** Unchanged.
- **External attackers cannot enumerate household topics** without first learning the root pubkey. The root pubkey is never sent in plaintext over the gossip wire (envelopes are signed by *agent* keys, not the root); it surfaces only inside sealed `PairGrant`s and in the direct host pairing handshake. So a random scanner cannot compute the catalog ids for a household it has not interacted with.
- **Cross-household correlation via shared id is impossible.** Because the root pubkey is part of the derivation, household A's `comms.email` and household B's `comms.email` have different topic ids. The host cannot link "these N tenants all subscribed to the email category" via shared id.

### 4.2 Properties weakened (the tradeoffs)

**4.2.1 Per-tenant category census, host-side.** The host knows each tenant's root pubkey (it *is* the tenant id) and its registered topic ids. With a published catalog, the host can compute `derive(cat, root)` for every catalog entry and label each tenant's well-known topics by category. The host learns "tenant X uses email, sms, and power telemetry."

We judge this acceptable because:
- Traffic-pattern analysis already leaks rough category signal (email is bursty and medium-sized; sms is small and frequent; telemetry is regular and small). The catalog labels make explicit what motivated traffic analysis would approximately recover.
- The leak is opt-in *per topic*: ad-hoc names (`home.notes`, `bedroom.cam`) remain random and uncategorized. Operators sensitive to a specific category can choose not to use the well-known name for it.
- Subpoena resistance changes from "host genuinely cannot say what categories tenants use" to "host could in principle reverse this offline." For operators who weight subpoena resistance heavily, §5 sketches a defense.

**4.2.2 Insider enumeration is cheaper.** A paired-in agent already holds the root pubkey (it travels inside `PairGrant`). Today, that agent does not know the id↔name mapping for topics it was not invited to. With a published catalog, it can compute the candidate ids for well-known categories and trial-join the corresponding gossip meshes to collect ciphertext.

It still cannot decrypt — no epoch key, no cap — but it can sit on the ciphertext for later (if a key ever leaks, the AEAD has a flaw, etc.). This is a real reduction in defense-in-depth, but bounded: a household-insider threat model was always thin (any compromised household agent could trial-join meshes by enumerating random ids if it really wanted to, though the search space was infeasible). What changes is the search space for the well-known subset shrinks from 2^256 to `|CATALOG|`.

### 4.3 Properties unchanged from today (good and bad)

- A household member with a cap for `comms.email` can read **all** retained history on `comms.email`, including messages from before they joined. (This is the host-replay behavior of substrate v1 — joining = "see everything the host still has." Forward-secrecy-on-add would require epoch rotation at `pair-approve` time, which is out of scope.)
- Topic *names* of ad-hoc (non-catalog) topics remain CLI-side conveniences with zero wire presence.

## 5. Future option: per-household salt

If the host-side category leak (§4.2.1) becomes load-bearing for some deployment, the derivation can swap `root_pubkey_bytes` for a household-generated random salt that ships only inside `PairGrant`s and is never sent to the host. The host then sees opaque ids it cannot reverse into categories.

We propose **deferring this to v2**. v1 ships the simpler scheme; the migration path stays open because the derivation function is a single point of change in `wires-core::well_known`.

## 6. Considered alternatives

**A. Globally deterministic ids — `BLAKE3(category)` with no per-household salt.**
Rejected. Any internet attacker can compute the id and join the gossip mesh to collect ciphertext. The "topic id as a shared secret" defense-in-depth disappears entirely, leaving AEAD as the sole confidentiality layer. Also enables cross-household behavioral correlation via shared id (host sees write spikes correlating across tenants on the same id).

**B. Per-household directory topic.**
A reserved `__directory` topic on which the operator publishes "category `comms.email` → id `0xabc…`" entries; agents read the directory to find ids. Rejected for v1: adds a propagation mechanism (gossip + replay of directory entries, conflict handling for renames, version-vector semantics) and the user-visible gain over "compute the id from the catalog" is small. Could be revisited if catalog growth or per-instance scoping becomes important.

**C. Schemaful service types.**
Each catalog entry would carry a content schema, content-type tag, and required reserved message types. Rejected: LLM consumers handle schemaless content well, and formal schemas become long-lived bikeshedding magnets that delay shipping. The category name is the only coordination point; everything else is freeform.

**D. CLI opt-in flag — `wires topic create comms.email --well-known`.**
Rejected. The whole point of well-known is cross-agent discoverability: if Larry's agent says "subscribe me to `comms.email`," he must be able to compute the id *without* asking Alice. If Alice's `comms.email` is random unless she opts in, the catalog name no longer implies a derivable id. Determinism must be the default for catalog names; explicit opt-in defeats the purpose.

## 7. Implementation sketch

This is a sketch for sizing, not a plan. A separate `docs/superpowers/plans/` document will cover the task breakdown if this proposal is accepted.

| Crate | Change |
|---|---|
| `wires-core` | New `well_known` module: `CATALOG: &[&str]`, `is_well_known(&str) -> bool`, `derive(&str, &str) -> [u8; 32]`. Unit tests cover determinism, distinct categories, distinct roots, null-separator collision resistance, and the catalog membership check. |
| `wires-cli` | `cmd::topic::create` branches on `well_known::is_well_known(name)` to choose id source. Integration test: two data dirs initialized with the same root, both `topic create comms.email`, ids must match. |
| `README.md` | Add a sentence to the walkthrough explaining well-known names. |
| `CLAUDE.md` | Add well-known v1 to the status list. |

No wire-format changes. No new ALPNs. No host changes. No new dependencies (`blake3` is already in `wires-core`). Estimated effort: small — one new module of ~50 LOC plus tests, one branch in an existing function, two integration tests.

## 8. Open questions for reviewers

1. **Initial catalog content.** Strawman: `comms.email`, `comms.sms`, `comms.telephony`, `utility.power`. What else should v1 ship? Suggestions welcome — keep them service-category-shaped ("what the topic provides to the household"), not provider-shaped ("Twilio", "Google").
2. **Catalog governance.** Treat as additive-only — once a name is in, it stays forever — to avoid silent breakage of long-lived deployments? Or allow deprecation with a clear migration story?
3. **Collision with prior ad-hoc topics.** If a household already has a random-id `comms.email` predating the catalog, `wires topic create comms.email` should… (a) refuse, (b) shadow the old one with the new derived id, (c) leave the old id in place and warn? Recommendation: refuse — the operator deletes the old entry from `topic_names.json` and re-creates if they want to migrate.
4. **`wires status` UX.** Should well-known topics be flagged in `status` output (e.g. `comms.email  [well-known]  <id>`)? Low-cost addition; included if reviewers want it.
5. **Per-household salt — v1 or v2?** Defer to v2 unless someone identifies a deployment where the host-side category census is a hard blocker.
6. **Should the catalog be sorted / canonicalized at compile time?** Not load-bearing, but `assert!(CATALOG.windows(2).all(|w| w[0] < w[1]))` in a test prevents accidental duplicates and gives the human reader a single sorted list.

## 9. Decision request

Reviewers please weigh in on:

- The threat-model tradeoff in §4.2 — particularly the host-side category census. Is this acceptable for the deployments we care about?
- The catalog content (§8.1) and governance policy (§8.2).
- The collision policy (§8.3).
